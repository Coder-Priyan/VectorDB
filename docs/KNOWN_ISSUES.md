# Known Issues and Limitations

This document provides an honest assessment of current limitations, architectural trade-offs, and unresolved behaviors in VectorDB.

- **RAG answers from llama3.2 3B can hallucinate**: e.g., the model invents a definition of $M$ although the sample document never defines it; cause: there is no similarity score threshold, so the top-$k$ retrieved chunks are always injected into the context prompt regardless of relevance.
- **rag_eval scorer is weak**: `expect_any` and `forbid_any` lists are often empty for answerable questions, refusal evaluation relies on an exact-sentence match, partial answers and hallucinations lack dedicated labels, and the test suite contains only 14 questions; cause: its automated scores are not a statistically reliable quality metric.
- **HNSW cosine recall (0.612) is lower than Euclidean (0.81)**: observed at $d=128$ on synthetic Gaussian random data; cause: root cause is not yet isolated (control test pending).
- **HNSW speedup over brute force is limited at high recall**: HNSW is only ~1.07x faster than brute force at 0.972 recall ($n=20000, d=128$, random data); cause: benchmarks were executed on a single machine, single thread, single PRNG seed, and uniform Gaussian data where spatial indexing exhibits dimensionality curse.
- **Collection concurrency and lifecycle constraints**: Collection uses one global mutex (`std::mutex`); storage is strictly in-memory (no persistence); there are no delete or update operations; only plain-text documents are supported; `/api/docs` ingest is non-streaming; and CPU-only LLM generation is slow.
- **RagPipeline::ingest insertion is not atomic**: `RagPipeline::ingest` (in `src/rag.cpp`, step 4) is all-or-nothing only with respect to embedding generation failures (Ollama unavailable, dimension mismatch): embeddings are computed and validated (client: count, shape, finiteness, consistent dimension; pipeline: chunk count and configured dimension) before anything is stored. However, the vector insertion loop itself is not atomic: it calls `collection_->insert()` per chunk with no try/catch and no rollback (Collection provides no delete operation). If an insert threw mid-loop (practically only on out-of-memory), already-inserted chunk vectors would remain in the collection and be searchable via `/api/docs/search` and `/api/ask` without a corresponding `DocumentRecord` (they would not appear in `GET /api/docs` and `GET /api/docs/:id` would return 404), and the `docId` counter would be consumed. Only `POST /api/docs/reset` clears them.
- **Security model limitations**: No built-in authentication, TLS encryption, or request rate limiting; `Host` and `Origin` header validations apply only when bound to a loopback address (`--host 0.0.0.0` disables loopback `Host` header checks); Content Security Policy (CSP) is emitted as both an HTTP response header and HTML meta tag alongside `nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer`; prompt-injection in ingested document chunks is mitigated only by system prompt instruction wording.
- **Vendored third-party dependencies**: `third_party/httplib.h` (cpp-httplib v0.18.3) and `third_party/nlohmann/json.hpp` (v3.11.3) are vendored header-only libraries and have not been audited or synchronized against newer upstream releases.
- **Search path step trace availability**: Interactive search path step tracing (`POST /api/hnsw/trace`) is supported only on the Demo vector collection; document chunk collections do not record step-by-step layer hops.
- **HNSW canvas DOMException 11**: A `DOMException` `INVALID_STATE_ERR` (`drawImage` on a 0x0 canvas) was observed once in Google Chrome after navigating from another tab; it could not be reliably reproduced afterwards. A guard (`isCanvasDrawable` in `web/js/hnsw_helpers.js` and `requestAnimationFrame` re-measuring on tab activation) prevents the exception, but the exact initial layout trigger was not proven.
- **Browser UI test coverage**: Interactive browser UI workflows (SSE token streaming, citation card navigation, zoom/pan canvas, playback controls) are verified through unit tests of pure logic helpers and manual inspection in real Chrome; there are no automated browser end-to-end click tests (e.g. Selenium/Playwright).
